# PEWA-F03-PAP-001 — Architectural Trade-offs and Alternatives

| Question | Recommended principle | Alternative considered | Trade-off and reason |
|---|---|---|---|
| How should organisations be separated? | Require demonstrable isolation and organization-scoped authorization; defer the tenancy mechanism. | Commit now to shared database/tenant keys, separate databases, or one deployment per business. | Each may fit later needs, but selecting now would exceed F03 evidence. Requirements, threat model, data classes, operational capacity and shared identity/tenant readiness are not established. |
| Who controls menu and order truth? | Business controls supplied offering meaning and business decisions; PEWA owns responsibility for any product validation, presentation and behavior it performs. Keep canonical technical state ownership open. | Treat business authority as proof the business is canonical data store owner; or make PEWA the unconditional canonical owner. | Content authority and technical record authority are distinct. F01/F02 explicitly leave canonical menu/order state and technical storage/publishing responsibility unresolved. Prematurely choosing either would erase an open decision. |
| Should broader reusable offerings be designed now? | Maintain sector-neutral structured-offerings as a hypothesis; keep food-service as initial scope and F01 exclusions. | Build for generic commerce immediately; or hard-code every food-service difference as a separate bespoke product. | Generic commerce risks scope expansion; only bespoke food-specific logic may block reuse. F04 should test reusable capability boundaries against real food-service variations, not add unrelated domains. |
| Should organisation variation be configuration? | Prefer configuration when it expresses bounded, recurring variation; keep domain rules explicit. | Allow arbitrary custom code per business or force uniform behavior. | Configuration can improve reuse but excessive configuration becomes a hidden programming language; uniformity ignores legitimate context. No configuration schema or customisation model is selected. |
| Should PEWA consume MWA? | Keep MWA as the approved intended boundary, conditional on contract conformance, ownership, operational and access readiness. | Build a parallel Meta/provider stack in PEWA; or make WhatsApp required for product access. | A parallel stack conflicts with F01 and duplicates shared work. Mandatory WhatsApp contradicts optional channel direction and risks web availability. MWA code artifacts do not independently establish readiness. |
| How much provider portability? | Keep domain meaning independent where material risk warrants; use provider-specific implementation if switching cost/risk is proportionate. | Abstract all infrastructure for immediate replaceability; or embed provider-specific semantics throughout product truth. | Full abstraction adds cost without demonstrated risk; pervasive coupling can make migration/control costly. MTAIP-001 calls for deliberate, risk-based seams and no duplicate authoritative store. |
| What should shared-service reuse require? | Verify approved scope, owner, versioned contract, maturity, operations and PEWA access before relying on it. | Assume a candidate service is available from a draft catalogue or a repository artifact; or build a new shared service for every gap. | The first mistakes documentation/code for operating capability; the second creates duplication and speculative infrastructure. Reuse-first still requires actual fit and readiness. |
| What should failure isolation protect? | Keep independent web access available when optional messaging/shared dependencies fail; report product outcomes accurately. | Make web access depend on MWA or another common service; or duplicate all channel logic in PEWA. | Required dependencies create a failure cascade; duplication increases drift. Exact fallback behavior belongs to later product architecture and requirements. |

No alternative is selected as an implementation design. This record captures decision criteria for Founder review; the unresolved register identifies where evidence or authority must come from.
